统一知识平台 · 多源知识联邦

为什么需要统一知识平台

企业知识天然分散在四类平台：自建AI知识库（政策 / 模板 / 成果等核心资产）、ima 知识库（个人与团队资料沉淀、文章素材）、钉钉文档（内部协同与制度流程）、腾讯文档（对客交付物与跨组织协同）。顾问回答一个问题需跨平台翻找，而 AI 只覆盖其中一部分——知识资产越多，查找成本越高。

原则含义反模式（禁止）
① 不搬迁，只连接各平台保留为员工原有的使用与协作现场，平台只做连接与索引强制全员把文档搬到自建库——协作现场丢失、推行阻力极大
② 统一入口，单一答案上层只面对一个检索接口，多源结果融合去重后统一呈现四个平台四个答案，顾问需自行判断信哪个
③ 产出即沉淀文档 / 文章定稿后自动回流为可检索知识，形成正循环写完即弃，同类问题反复从零撰写

主次定位：自建AI知识库为主库（Source of Truth）与索引中枢——负责统一索引、融合排序、权限收敛与对外 MCP 输出；ima / 钉钉 / 腾讯文档为协作现场与增量来源。任一外部平台不可用时，核心知识资产与检索能力不受影响。

统一知识平台架构图（v2.6）

自上而下六层：应用 → 融合 → 索引 → 接入（适配器隔离第三方差异）→ 同步 → 沉淀。上层只见一个检索接口，底层差异全部由适配器吸收。

三种接入模式与联邦检索

接入模式适用做法取舍
A. 原生托管自建库直接写入统一索引，结构化字段完备质量最高，需录入人力
B. 镜像同步（推荐优先）钉钉文档、腾讯文档导出 markdown → 规范化 → 入自建索引，保留 origin_url 回链检索质量高、可离线、支持统一重排；需处理增量与配额
C. 检索代理（兜底）导出受限或成本过高不搬运原文，实时转发检索请求，结果归一化为 CanonicalDoc 参与融合排序零存储、始终最新；受源平台检索能力约束，不可离线

决策规则：能镜像则镜像，不能镜像才代理。镜像模式保证检索质量可控（统一分块 / 向量 / 重排），是「单一答案」目标的前提；代理模式仅用于补充长尾来源。ima 采用混合模式——平台侧维护索引镜像用于融合排序，写入侧直接调用 add_knowledge 保证与用户在 ima 端操作一致。

联邦检索链路：意图与分域识别 → 源路由选源+权重 → 并行检索 N 源 → 分数归一化 → RRF / 重排融合 → 权限过滤 + 去重 → Top-K + 引用溯源

关键设计：各源分数分布不同（向量余弦 vs BM25 vs 平台自有分），必须先归一化再融合，否则高分源会系统性压过其它源；单源超时 / 限流时标记「该源未参与本次检索」并提示，不阻塞整体返回。

文档 / 文章撰写 → 知识沉淀闭环

统一平台从「能查」到「越用越强」的关键：让每一次撰写都变成资产，而不是消耗。

文档Agent生成初稿 → 人工定稿（协作平台） → 定稿事件触发沉淀管线 → 抽取 → 评分 → 准入 → 去重 → 回写 → 索引+审计

沉淀分级内容范围处理方式对外 MCP 可见
① 公开可复用政策解读 / 模板 / 方法论 / 通用文章入全库✅ 是
② 含客户信息项目交付物 / 案例脱敏后入模板库 · 成果库，原文留项目库且仅内部可见⚠️ 仅脱敏版
③ 敏感档案客户档案 / 财务数据不沉淀，仅项目内可见❌ 否

质量准入：引用率 ≥1 条可溯源依据、重复率 <30%、质量分 ≥85 才入库，未达标进「待完善」队列；条目版本化管理可回滚；贡献人采纳率纳入绩效与专家评级；反哺写作——沉淀条目在下次撰写同类文档时自动进入 RAG 上下文，同类文档撰写耗时随沉淀量递减。

公告智能体与 MCP 对外出口

需求原文：①专家公告运营加 AI 智能搜索；②高级与基础用户在公告模块加 AI 分析；③规划一个可接入 WorkBuddy / 千问办公的 Agent 助手。

🔴 核心判断：本需求 ≠ 接大模型。平台 AI 全部是确定性规则引擎、零 LLM 调用（演示环境单端口、无 env 注入）。因此设计重点不是"调模型"，而是引擎分层：①规则内核（唯一接触数据、唯一做可见域过滤）②平台编排 ③外部 Agent 接入。三轨 AGENT_MODE=off|rule|remote 共用同一响应 schema，差异只体现在 engine / confidence 两个字段。

#铁律落法

🔴 上线实测踩到的坑：云沙箱网关会覆写 Authorization

首发上线后 /api/mcp/health 已是 200（证明新代码生效），但六个 key 全部 401——连确定有效的 premium/basic/admin 也一样，而本地同一份代码、同一张表、同一批 key 58/0 全绿。

排查步动作结论
① 查数据直连 PostgREST 读 mcp_key5 行、hash 与明文 sha256 逐条命中 → 排除数据问题
② 读文案看返回是「无效或已停用」而非「需要 API key」两条不同分支 → 服务端拿到了值但值不对 → 请求被改写
③ 回源码搜 authorization既有注释白纸黑字：云沙箱网关会覆写 Authorization（故平台自家接口一律用 X-Auth-Token）

修法：改为自定义头优先 + 候选逐一试配，线上用 X-MCP-Key，Bearer 仅作自建/直连回退；回归脚本请求侧一并改掉（否则"本地绿、线上红"），并补两道防回退断言。通用教训：本地门禁只能覆盖"应用内"行为，覆盖不到宿主对请求本身的改写——凡新引入"靠 HTTP 头传凭据"的通道，必须做一次本地全绿 → 线上实测的对照。

安全设计

AI 三重失控应对

人对AI失控：MCP工具粒度权限 + 高风险操作二次确认 + 全审计
AI自身失控：高风险"模型提议+确定性代码执行" + 输出引用溯源 + 置信度阈值转人工
数据泄露：脱敏后入语料 + 检索权限前置 + 本地部署数据不出内网

红队测试（上线门禁）

四类攻击模拟：Prompt注入绕过权限（garak/promptfoo）、Token配额DoS（k6压测）、越权操作诱导、外网内容投毒。高危项清零才可上线，测试记录归档作为监管证明。

存储加密：MinIO SSE-KMS ｜ PostgreSQL pgcrypto 字段级加密 ｜ Redis 不存 PII。
